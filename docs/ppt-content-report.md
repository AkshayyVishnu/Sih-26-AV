# PART A — Comprehensive Project Report

## A.1 Problem statement (condensed)

PS 26037 asks for a simulated, closed-loop autonomous-driving system
that can plan and drive safely on **unstructured Indian roads**: mixed
traffic (cars, buses, trucks, auto-rickshaws, two-wheelers, bicycles,
pedestrians, pushcarts, animals), unclear or missing lane markings,
informal merging, sudden direction changes, and unmarked pedestrian
crossings. The system must perceive with a multi-sensor setup (camera +
LiDAR, radar optional), predict short-term motion of irregular/
non-lane-based agents, generate a collision-free path with real-time
replanning, and be validated on **at least 5 realistic scenarios**:
unmarked village road, busy unsignaled urban intersection, highway merge
with slow-moving vehicles, dense mixed-traffic market area, and a sudden
cattle-crossing event. Required deliverables: a working simulation
pipeline, ≥2 detailed authored scenes, performance metrics (replanning
latency, path smoothness, scenario completion rate), a technical report,
and a demonstration video.

## A.2 System architecture & data flow

The project implements this exact closed loop, once per simulation tick
(`pipeline/pipeline.py`'s `Pipeline.tick()`):

```
Sensors (Camera + LiDAR + Semantic Segmentation)
   -> Perception Fusion   (LidarCameraFuser: projects 2D detections into
                            the LiDAR point cloud, classical geometry,
                            no learned model)
   -> Multi-Object Tracking (MultiObjectTracker: Hungarian assignment +
                            per-object Kalman filter, consistent track
                            IDs + velocity)
   -> Motion Prediction    (ConstantVelocityPredictor: 3 modes per
                            object -- straight + two uncertainty-scaled
                            lateral offsets, per-class uncertainty)
   -> Drivable-Area Estimation (DrivableAreaEstimator: classifies LiDAR
                            points on/off-road via segmentation tags --
                            critical on roads with no lane markings)
   -> Decision Logic       (DecisionLogic: hierarchical state machine --
                            NORMAL_DRIVE / OBSTACLE_DETECTED /
                            ANIMAL_ON_ROAD / EMERGENCY_BRAKE (parallel
                            with) REPLAN / RESUME, debounced entry,
                            sustained-clearance exit, independent
                            SAFETY_SUPERVISOR watchdog)
   -> Path Planning        (Planner: local costmap + 8-connected A*,
                            soft obstacle inflation, replans only on
                            significant scene change or a decision-layer
                            request)
   -> Low-Level Control    (PurePursuitController: geometric steering +
                            proportional speed control, curvature-aware
                            slowdown)
   -> Vehicle Motion       (CARLA's own PhysX vehicle physics)
   -> loop back to Sensors
```

Two clean integration boundaries make this modular and independently
testable:
- **`pipeline/`** is **100% CARLA-free** — pure Python + NumPy, testable
  against synthetic data with zero simulator dependency (`run_demo.py`).
- **`carla_runtime.py`** is the *only* place that imports `carla` — all
  sensor spawning, coordinate-frame conversions, and the ground-truth
  perception stand-in live here, shared by every entry point.

Every tick's per-stage latency is logged and summed; the pipeline itself
warns in real time if a tick exceeds the **150-200ms** threshold
identified as the point where closed-loop success rate collapses in
comparable research (this is the project's own explicit, self-enforced
design ceiling).

## A.3 Implemented tech stack

| Layer | Technology |
|---|---|
| Simulator | **CARLA 0.9.16** (synchronous mode, fixed timestep) |
| Core pipeline language | Python 3.12, NumPy 1.26.4 |
| Multi-object tracking | `filterpy` (Kalman filter, constant-velocity model) + `scipy.optimize.linear_sum_assignment` (Hungarian algorithm) |
| Perception (target) | Ultralytics YOLOv8/v11 (`ultralytics==8.2.58`) + PyTorch 2.3.1 / TorchVision 0.18.1 — fine-tuning target datasets: **DATS_2022** + **IDD** |
| Perception (current stand-in) | `GroundTruthDetector` — projects CARLA's own actor bounding boxes into the camera frame, same output shape a real detector would produce (no fine-tuned checkpoint exists yet) |
| Path planning & control | Hand-rolled 8-connected grid A* with soft costmap inflation + Pure Pursuit controller — zero external solver dependency, zero license risk |
| Live visualization | `pygame` — custom 2x2 debug dashboard (`viz.py`), no OpenCV/matplotlib GUI thread |
| Decision logic | Hand-rolled Python state machine, designed as a 1:1 mirror of a Stateflow chart |
| Planning/control "AI-enhancement" track | **MATLAB/Simulink** toolbox stack — Stateflow, Navigation Toolbox, Model Predictive Control Toolbox, Deep Learning Toolbox, Computer Vision Toolbox, Sensor Fusion and Tracking Toolbox, Automated Driving Toolbox — connected via **direct Python interoperability** (`py.*`/`pyrun`) rather than a ROS bridge |
| Motion prediction (extension point) | **MoFlow** (CVPR 2025, IMLE student model, 0.70ms/prediction, MIT license) — interface reserved, not yet wired to a checkpoint |
| Benchmark/comparison agents | **PCLA** (41 bundled pretrained CARLA driving agents, Apache-2.0) — TransFuser v6 (full end-to-end) and PlanT2 (object-level planner) specifically integrated |
| Metrics | Custom `MetricsRecorder` (CSV per-tick + JSON summary per run) + `metrics_export.py` (cross-run aggregation) |

**Why direct Python interop over a ROS bridge**: failure-mode research
found that nearly every documented integration bug in the
MATLAB-Simulink + CARLA stack lives *inside* `ros-bridge` itself
(including an unresolved crash — `bad_alloc` — specific to Simulink's
ROS subscriber consuming CARLA image topics). Removing that middleware
layer removes the whole bug category, not just mitigates it. ROS Toolbox
+ `ros-bridge` is retained as a documented fallback only.

**Why nothing here needs training from scratch**: every AI component in
the architecture has a usable pretrained starting point — YOLOv8/v11
(COCO-pretrained), MoFlow (ETH-UCY/SDD/NBA-pretrained), and PCLA's 41
bundled checkpoints. The real work is fine-tuning two of these on
Indian-road data, not building any of them from zero (a from-scratch
comparable, e.g. UniAD/VAD, would cost on the order of 3,000+ GPU-hours
— explicitly not attempted).

## A.4 Modular scenario/autopilot framework (`framework/`)

Built as a parallel, additive layer (the original `Simulation Files/`
scripts remain untouched and still work) around two independent,
swappable axes:

- **`Scenario`** — *what happens in the world* (actors spawned, scripted
  events). Never makes a driving decision.
- **`Autopilot`** — *what drives the ego* (sensor data in, a control
  command out). Never spawns actors or scripts events.

`ScenarioRunner` is the shared engine (CARLA connect, sync mode, ego +
sensor spawn, the tick loop, the debug dashboard, cleanup, metrics
recording) — written once, reused by every scenario × autopilot
combination. `TickContext` is built exactly once per tick and shared by
both the scenario and the autopilot, specifically to eliminate a
measured problem: the same actor's transform being fetched 2-3 times per
tick from different call sites in the pre-framework code.

**Four registered, swappable autopilots** — the core of this project's
comparative-evaluation story:

| Autopilot | What it does | Purpose |
|---|---|---|
| `pipeline` | This project's own perception → A* planner → Pure Pursuit stack | The primary, fully-owned solution |
| `pcla_tfv6` | PCLA's bundled TransFuser v6 (fully end-to-end, sensor-to-control) | Independent reference point — a strong published baseline |
| `own_perception_plant2` | This project's own perception feeding PCLA's PlanT2 planner (via a monkey-patched injection point, everything else in PlanT2 untouched) | Fair, apples-to-apples test: "is our own planner competitive with a learned one, holding perception constant?" |
| `plant2_ground_truth` | PlanT2 with its own unmodified ground-truth perception | A **ceiling** — the gap between this and `own_perception_plant2`'s results isolates how much performance is lost to this project's own perception specifically, vs. planning quality |

**`SafetyEnvelope`** — an independent, ground-truth-based
time-to-collision watchdog wrapping every PCLA-backed autopilot's raw
output. It can force a full emergency brake (steering preserved) without
touching the wrapped policy's own reasoning at all — the standard
real-world pattern for supervising a learned/opaque driving policy with
an independent monitor.

## A.6 Metrics & results

Three metrics are tracked automatically for every scenario × autopilot
run, matching the PS's own named metrics exactly, via
`pipeline/metrics.py`'s `MetricsRecorder` (wired into `ScenarioRunner`
for every `framework/` run):

1. **Replanning latency** — total pipeline tick time (ms), all 7 stages
   individually broken out.
2. **Path smoothness** — jerk (rate of change of acceleration, m/s³),
   computed against the fixed simulation timestep (not wall-clock — this
   is important, and was a caught-and-fixed bug: wall-clock jerk is
   nonsensical when the CARLA world always advances by exactly `dt` per
   `world.tick()` regardless of client-side processing speed).
3. **Scenario completion rate** — reaching within a configurable radius
   of the scenario's final goal, plus collision count/actor from a
   dedicated collision sensor.

`metrics_export.py` aggregates these across multiple runs into one
report (mean/max latency, mean jerk, completion %, total collisions),
explicitly warning if any scenario has fewer than 3 recorded runs
(closed-loop AV results are seed-sensitive — this project follows the
same "≥3 seeds before reporting a number" discipline documented in
`carla_garage`'s own common-mistakes guide).

**Honest status of the numbers below**: the metrics *instrumentation* is
built, wired in, and has been exercised live. A polished, ≥3-seed,
`metrics_export.py`-aggregated report has not yet been generated in this
environment (no live CARLA server available here). The figures below are
real, directly observed numbers from actual runs, reported narratively
rather than pulled from a surviving structured CSV:

| Run | Environment | Result |
|---|---|---|
| Design ceiling (target, not measured) | — | **150-200ms** total tick latency — the threshold beyond which comparable closed-loop AV studies show success rate collapsing from ~95% to under 10% |
| `run_demo.py` (synthetic, zero CARLA) | Dev machine | Steady-state **~8-10ms/tick** total latency; one cold-start tick ~28ms (isolated, non-reproducible OS/AV-scan artifact, not an algorithmic issue) |
| Original `scenario_2.py` (pedestrian jump-out, live CARLA) | Dev machine, CARLA 0.9.16 | **~1.1-1.6ms/tick** client-side processing, trigger fires correctly, zero leftover actors on shutdown |
| `framework/run_scenario.py pedestrian_jumpout` | Dev machine, CARLA 0.9.16 | **~5.3ms/tick mean** over 1074 ticks, trigger fires, sustained multi-object tracking, zero leftover actors |
| `framework/run_scenario.py traffic_stress` | Dev machine, CARLA 0.9.16 | **~5.5ms/tick mean** over 373 ticks with 265 vehicles + 3 walkers spawned, zero leftover actors, traffic lights correctly restored |

**Headroom**: every measured figure sits **15-30x below** the 150-200ms
ceiling, on both synthetic and live-CARLA runs, with the framework's own
extra bookkeeping (`TickContext`, metrics recording) adding only ~4ms of
overhead over the original scripts.

## A.7 Known limitations / disclosed shortcuts

Documented plainly, not hidden — presenting these accurately is itself
evidence of engineering rigor:

- **No fine-tuned YOLO checkpoint exists yet** — `GroundTruthDetector`
  (projecting CARLA's own actor bounding boxes into the camera frame)
  stands in for real perception everywhere today. The `Autopilot`
  interface doesn't care how detections are produced, so swapping in a
  real model later touches one class, not the pipeline.
- **Drivable-area detection uses CARLA's own ground-truth segmentation**,
  not a learned segmentation model — an explicit, disclosed
  simulation-only shortcut (the production equivalent would be a
  fine-tuned DeepLab/SegFormer-class model).
- **Tracker is Kalman + Hungarian assignment**, not a full JPDA/IMM
  implementation — adequate for the current scenarios; the first place
  to upgrade if track-ID swapping shows up under dense, crossing traffic.
- **Two real bugs found and fixed during development** (kept here as
  evidence of live-testing rigor, not just design-on-paper): a
  camera↔LiDAR extrinsic sign error (confirmed against CARLA's own
  reference examples), and a time-to-collision calculation that measured
  distance from the world origin instead of from the ego vehicle
  (invisible on synthetic data where the fake ego sits at the origin;
  would have silently broken every hazard-mode decision on the first
  real CARLA map).
- **No livestock 3D asset exists in stock CARLA** — `cattle_crossing`'s
  "herd" is ordinary pedestrian-walker blueprints relabeled via
  `role_name="livestock"` so the perception/decision layers correctly
  classify them as "animal."
- **3 of the 5 PS-required scenarios still need one live-CARLA session**
  to capture real spawn/goal coordinates (Town07/Town10HD maps have not
  yet been loaded in this dev environment) — a mechanical capture step
  via `Simulation Files/carla_print_coordinates.py`, not a missing
  design.
